Diplomacy Lab
=============

Diplomacy Lab turns webDiplomacy into a free tactical analysis board, the way an online chess
site turns a chess engine into an analysis board. You build any position you like, give every
power its orders, adjudicate, look at the result, and step straight back to where you were.

The guiding rule of the implementation is: reuse webDiplomacy, do not reimplement it. In
particular the adjudicator is untouched, and remains the only source of truth for the rules.


The board is the application
----------------------------

Opening the Lab lands you on webDiplomacy's modern board - the React app in beta-src/, the same
one the site itself uses - with the Lab's own controls on top of it. There is no list of
positions to go through first and no separate editor page: everything happens on the map.

  EDIT POSITION   A click puts a unit on a province or takes what is there away. Land gives an
                  army, sea gives a fleet, and clicking a coastal province again turns its army
                  into a fleet - or, where there is more than one named coast, moves the fleet
                  round them. The Unit / Centre / Erase tools and the row of powers say what a
                  click means. Positions are free: a power may have no units at all, and unit
                  counts need not match supply centres. Only geography is enforced, by the
                  server, and a refusal is shown in the panel in the server's own words
                  ("Munich cannot hold a fleet.").

  ORDERS          The board behaves exactly as webDiplomacy's board always has: click a unit,
                  pick Hold / Move / Support / Convoy from the flyout, click where it is going.
                  Orders save themselves. Because a Lab board is a sandbox game, every power's
                  orders are entered from the one board.

  RESOLVE         Adjudicates through the ordinary engine and moves the board on to the position
                  that came out of it. The phase controls at the bottom of the board step back to
                  the phase that was just resolved, where the arrows, bounces and supports are.

RESET, DUPLICATE, SAVE and NEW sit alongside them, so a whole line of analysis - build, order,
resolve, look, step back, try something else - never leaves the board.

lab.php is still there, and still does everything it did: it is the place to list saved
positions, import and export JSON, set the year and season, and delete boards. It is no longer
where the work happens.


What the Lab reuses unchanged
-----------------------------

Almost everything the Lab needs already existed as part of webDiplomacy's sandbox games:

  * The board itself. beta-src/ is webDiplomacy's modern board, unchanged in how it draws the
    map, the units, the arrows and the orders. The Lab adds one panel (WDLabPanel) and one
    branch in the province click handler (WDProvince); everything else on screen is the board
    the site already had.

  * The classic position editor. javascript/canvasBoard.js is webDiplomacy's own click-a-province
    map editor, written for gamecreateSandbox.php's "custom unit assignments". lab.php still
    drives the same script, so the fallback editor behaves exactly as it does when creating a
    sandbox.

  * Geographic validation. gamecreateSandbox.php already refuses armies at sea, fleets in
    landlocked provinces and two units in one province, and handles coast parents and children.
    LabPosition::validate() applies the same rules, reading the map from wD_Territories so it
    follows whatever the variant's own install script defined.

  * Order entry for every power at once. board/orders/orderinterface.php drops its countryID
    filter when isSandboxMode is set (see its load() method), so a sandbox board shows the orders
    of all seven powers together, colour-coded by country.

  * One Ready for all powers. The same file's writeOrderStatus() already readies every member of
    a sandbox game at once.

  * The adjudicator, the map, the arrows, the supports/convoys/bounces display, and the results.
    None of these are modified in any way.

  * Cloning and erasing boards: gamemaster/sandboxGame.php.

  * Docker. docker-compose.yml is used as-is.


What the Lab adds
-----------------

Four things were genuinely missing, and they are what the Lab code provides.

1. An arbitrary year, season and phase.
   In webDiplomacy the calendar is just wD_Games.turn. For Classic,
   variants/Classic/variant.php maps turn to a date as
       turn = (year - 1901) * 2 + (Autumn ? 1 : 0)
   so choosing a year and season is only a matter of setting the turn.
   LabPosition::turnFromYearSeason() does that conversion.

2. Editing the position of a board that already exists.
   gamecreateSandbox.php applies its custom assignments once, while creating the game.
   LabPosition::applyToGame() does it to a live board, at any time.

3. Immediate adjudication.
   Readying orders normally just leaves a hint for the gamemaster cron. processLabGame::resolve()
   readies every country that has orders this phase and calls processGame::process() directly.

4. An exact reset point.
   processGame::moveTurnBack() replays webDiplomacy's turn archives, which only goes back one
   turn and depends on that history being intact. The Lab instead snapshots the position as JSON
   immediately before adjudicating (wD_LabGames.snapshotJSON) and restores it by simply applying
   that position again. RESET therefore returns to exactly the board you built.


The one behavioural change, and why
-----------------------------------

processGame::changePhase() eliminates any country with no units and no supply centers
(findSetDefeated()), and ends the game when only one country is left standing
(checkForWinner()). When a game ends, processGame::process() deletes every unit on the board.

In a lab that is wrong. A position with only France and Germany on the map has to keep working,
and so does a single power practising against an empty board. processLabGame::changePhase()
therefore reproduces the phase-transition half of the original exactly and skips only the
defeat/victory half. Nothing in gamemaster/adjudicator/ or gamemaster/orders/ is touched, so the
rules, and the DATC results, are unaffected.

The other adjustment is the clock. The gamemaster picks up any game whose processTime has passed,
and processGame::process() resets processTime to one phase length after each adjudication. A Lab
board must never adjudicate itself while you are not looking, so processLabGame::freezeClock()
pushes its process time ten years out after every change. Only pressing RESOLVE resolves a board.

Note that pressing the board's own Ready button (rather than the Lab's RESOLVE) will also
adjudicate, via the ordinary sandbox path, but does not record a new reset point. RESOLVE is the
button to use.

One fix outside the Lab
-----------------------

Members->ByUserID holds one member per user, so in a sandbox game - where one user holds every
country - it names whichever country happens to sort first. Members::load() orders by supply
centre count, so that country changes the moment a centre changes hands. Three API entries
(game/data, game/status, game/getmessages) used it to decide whether the caller may ask about a
country, which meant a Lab board could refuse to load itself immediately after a supply centre
was given away. They now ask ByCountryID whether that country belongs to the caller, which is
the question that was meant and behaves identically for an ordinary game, where a user holds one
country. game/status already used ByCountryID on the line after the check.


Database
--------

Two new tables, and no changes to any existing table:

  wD_LabGames       One row per Lab board: its user-visible name, its owner, and snapshotJSON,
                    the position as it stood immediately before the last RESOLVE.
  wD_LabPositions   Positions the user has saved by name, as JSON.

lib/lab.php creates both on demand (CREATE TABLE IF NOT EXISTS), so an existing database does not
need to be migrated by hand.

A Lab board is an ordinary webDiplomacy sandbox game: a row in wD_Games with
sandboxCreatedByUserID set, and seven wD_Members rows all belonging to the one user. That is why
the existing board, order interface and map all work with it unchanged.


The JSON position format
------------------------

This is the format used by Export JSON, Import, saved positions and the reset snapshot. It is
also the format an external program or model would produce to set up a position. What follows is
all a position needs; a position read back out of a live game carries more, described under
"Snapshots" below.

  {
    "format": "diplomacy-lab-position",
    "formatVersion": 2,
    "name": "France Germany Belgium test",
    "variant": "Classic",
    "variantID": 1,
    "year": 1903,
    "season": "Fall",
    "phase": "Diplomacy",
    "turn": 5,
    "units": [
      { "country": "France",  "countryID": 2, "type": "Army",  "territory": "Picardy",          "terrID": 26 },
      { "country": "France",  "countryID": 2, "type": "Fleet", "territory": "English Channel",  "terrID": 61 },
      { "country": "Germany", "countryID": 3, "type": "Army",  "territory": "Ruhr",             "terrID": 41 }
    ],
    "centers": [
      { "country": "France",  "countryID": 2, "territory": "Paris",  "terrID": 27 },
      { "country": "Germany", "countryID": 3, "territory": "Munich", "terrID": 40 }
    ]
  }

Reading it is deliberately forgiving:

  * Territories may be given as "territory" (by name) or "terrID" (by ID). Names are matched
    case-insensitively and coasts are named as the variant names them, e.g.
    "Spain (North Coast)".
  * Countries may be given as "country" (by name) or "countryID". "Neutral" is accepted.
  * The calendar may be given as "year" plus "season", or as a raw "turn". "turn" wins if both
    are present. "Fall" and "Autumn" both mean the same season.
  * "phase" accepts the Lab's names as well as webDiplomacy's: "Retreat" is "Retreats" and
    "Adjustment" is "Builds".
  * "centers" is optional. Any supply center not listed is neutral.
  * Only geography is enforced. A power may have no units; unit counts need not match supply
    center counts; the position need not be reachable in a real game.

So the minimum a generator has to produce is:

  {
    "year": 1903, "season": "Fall", "phase": "Diplomacy",
    "units": [ { "country": "France", "type": "Army", "territory": "Picardy" } ]
  }


Snapshots: the rest of the state (format version 2)
---------------------------------------------------

A position built in the editor is only units, supply centers and a date, and everything else is
worked out when it is applied. That is all version 1 of the format had, and it is enough for a
Movement phase - but not for the two phases that are consequences rather than starting points.

A Retreats phase is not "some units are marked as retreating". It is a specific unit dislodged, a
territory the unit that dislodged it came from (which it may not retreat into), and the standoffs
that block other destinations. And while the retreat is pending, two units share one territory:
the dislodged one has not moved, and the one that dislodged it has. A Builds phase is each power's
unit and supply center counts, and the orders those counts entitle them to.

None of that survives being recalculated, so a position read out of a live game carries it:

  "territoryStatus": [
    { "territory": "Burgundy", "terrID": 48, "countryID": 2, "standoff": false,
      "occupiedFromTerrID": 41, "occupyingUnit": 1, "retreatingUnit": 0 }
  ],
  "orders": [
    { "countryID": 2, "type": "Retreat", "unit": 0, "toTerrID": 50,
      "fromTerrID": null, "viaConvoy": "No" }
  ],
  "members": [
    { "countryID": 2, "status": "Playing", "orderStatus": "",
      "supplyCenterNo": 2, "unitNo": 1 }
  ]

"occupyingUnit", "retreatingUnit" and an order's "unit" are *indexes into the "units" list*, not
territory or unit IDs. They have to be: unit IDs change when a position is written into a game,
and during a Retreats phase no combination of country, type and territory picks out one unit,
because two of them are standing in the same place.

Restoring a position that carries these puts them back exactly and recomputes nothing - in
particular the order generator is not run, because it would throw the orders away and hand out
empty ones. Restoring a position without them behaves exactly as version 1 did. A version 1 file
still loads: no "territoryStatus" simply means a position that was built rather than played.

This state belongs to the engine, and the Lab offers no way to write it by hand. Editing a
position discards it (LabPosition::clearEngineState), and the editor refuses to touch a board that
is not on a Movement phase, because a retreat or an adjustment only means anything as the outcome
of the phase before it. The freedom is in choosing a starting position; what follows from it is
the adjudicator's.


API
---

The Lab page itself uses plain form posts, but the same operations are available over the API
for scripting, at api.php?route=... . All of them check that the position belongs to the caller.

  lab/create        GET  variantID, name         -> { gameID, name }
  lab/position      GET  gameID                  -> the position, in the JSON format above
  lab/setPosition   JSON gameID, position        -> the position as stored
  lab/editProvince  GET  gameID, terrID, tool,   -> { gameID }
                         countryID, unitType
  lab/resolve       GET  gameID                  -> { gameID, turn, phase }
  lab/reset         GET  gameID                  -> { gameID, turn, phase }
  lab/duplicate     GET  gameID, name            -> { gameID, name }
  lab/save          GET  gameID, name            -> { positionID, name }
  lab/delete        GET  gameID                  -> { gameID }

lab/editProvince is one click on the board. tool is "unit", "center" or "erase"; unitType is
"Auto", "Army" or "Fleet"; countryID 0 means neutral, which empties the province or leaves the
centre unowned. Any territory of a province may be given: the server normalises it to the
province and picks the right coast itself, so the board does not have to know the map's rules.
A refusal comes back as plain text with an error status, which is what the board shows.

A headless "give me a position and orders, return the result" entry is not implemented, but the
pieces it needs are all here: LabPosition to read and write the board, and processLabGame::resolve()
to adjudicate. It would be a matter of creating a board, applying a position, writing the orders
through the existing OrderInterface, resolving, and reading the position back.


Phases
------

Diplomacy is complete. Retreats and Builds work through the same machinery, because the Lab
leaves webDiplomacy's phase transitions alone: adjudicating a Diplomacy phase with dislodged
units moves the board to Retreats by itself, and an autumn turn with a unit/supply-center
difference moves it to Builds by itself, exactly as in a normal game.

Retreats and Builds cannot be *set up* from scratch, and deliberately so. A retreat is the
consequence of a particular attack succeeding, and an adjustment the consequence of a year's
gains and losses; neither is a position anyone chooses. So the editor works on Movement phases
only, and the way to reach the other two is to resolve into them. Once reached they snapshot and
restore exactly (see "Snapshots" above), which is what lets you return to one and carry on.
